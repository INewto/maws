# MAWS

**Beta.** Фреймворк в разработке, версии 1.0 нет. API, имена классов и раскладка каталогов могут
меняться без обратной совместимости. Для продакшена — только после собственной проверки.

MAWS (Man, Ai, World, Screen) — PHP-фреймворк, построенный на явной метафоре человеческого тела:
голова прокладывает маршрут, ноги идут к месту, руки берут его инструменты, экран рисует сцену.
Три опоры (Man, World, Screen) — для стандартной разработки серверной логики; слой Ai — для
фоновых процессов агентской работы.

Описание архитектуры и правила работы — в [FORLLM.md](FORLLM.md).

Слой Ai разобран отдельно в [руководстве, глава 13 «Агенты»](MAWS-guide.html): как запустить агента,
откуда берётся задача, как он получает инструменты и где подключается модель.

## Требования для MAWS

| Что | Требование | Почему именно так |
|---|---|---|
| PHP | **8.1** и выше | `readonly`-свойства в конструкторах, `never`-возвраты, `array_is_list`. Ниже 8.1 ядро не собирается. |
| Composer | **`composer install`** до первого запуска | Опоры лежат в `vendor/`: Guzzle (HTTP-хелпер), `voku/portable-ascii` (транслитерация в `Text::slug`) и разбор JSON5 (`colinodell/json5`). Без `vendor/autoload.php` не поднимется ничего. |
| Расширения PHP | **`pdo_pgsql`, `mbstring`, `json`** | Без первого нет соединения с базой; без `mbstring` рвётся русский текст в `Text` и `Csv`; `json` — конфиги и ответы. |
| Расширение `gd` | по желанию | Нужно только `Image` и `Upload`: без него сайт живёт, картинки — нет. |
| База данных | **PostgreSQL** (любая поддерживаемая версия) | Проверка доступа инструмента к таблицам опирается на имя таблицы, которое называет сам движок в плане запроса. Не всякий движок его называет — см. ниже. |

Конфиги фреймворка — `settings.json`, `dbase.json`, `dbaccess.json`, `config.json`, а также политика
сессии в `core/System/Session/config.json` — читаются как **JSON5**: в них можно писать комментарии и
ставить запятые в конце перечислений. Строгим JSON такой файл уже не является, поэтому сторонние
редакторы и линтеры могут на нём ругаться — это ожидаемо.
Данные, приходящие извне (тело HTTP-ответа, ответ модели, колонки базы), по-прежнему разбираются
строгим `json_decode`: послабления нужны файлам, которые правит человек, а не потоку.

### Почему требование к базе именно такое

Место объявляет в `dbase.json`, какие таблицы разрешены его инструментам; у агента тот же механизм,
а права лежат в `dbaccess.json` рядом с агентом. Перед выполнением
запроса фреймворк спрашивает у движка `EXPLAIN (VERBOSE, FORMAT JSON)` и сверяет полученные
имена таблиц с объявленным списком. Разбирать SQL текстом при этом не нужно — поэтому алиасы,
JOIN, подзапросы и UNION проверку не обходят.

Правило строгое с обеих сторон. План, задевший необъявленную таблицу, — отказ; план, не назвавший
**ни одной** таблицы, — тоже отказ (`DbasePlanless`). Так потому, что по плану нельзя отличить
«запрос и не собирался трогать таблицы» от «план погашен»: `… WHERE false` и `SELECT 1 WHERE false`
дают один и тот же пустой план. Бестабличный случай не угадывается, а называется явно.

Инструкции, которым `EXPLAIN` плана не даёт вовсе (`TRUNCATE`, `ALTER`, `CREATE INDEX`, `DROP`),
отдельных методов не имеют: операции со схемой — дело миграций (`db/migrations`), а не инструмента.
Объявление таблицы в `dbase.json` — разрешение работать с её данными, поэтому `TRUNCATE` и `DROP`
остаются за границей: они стирают не данные, а саму таблицу вместе со связями. Поданные в
`all`/`one`/`run` текстом, такие инструкции получают именованный отказ по первому слову, не доходя
до сервера.
Бестабличный `select` выполняет
`selectUnplanned($sql)`: он требует пустой план и идёт в транзакции `SET TRANSACTION READ ONLY`,
поэтому `SELECT 1 INTO new_table` движок не пропустит. `all`/`one`/`run` принимают только те запросы,
у которых план вообще бывает (`select`, `insert`, `update`, `delete`, `values`, `merge`, `with`,
`table`) — остальное получает именованный отказ, а не сырую ошибку сервера. Обхода сверки произвольным
SQL во фреймворке нет. Граница названа: функции, чьи чтения план не показывает (встроенные `pg_read_file`
и прочие у суперпользователя), проверкой по плану не покрыты.

Проверка держится на том, что движок **строит план запроса и называет в нём таблицы**: PostgreSQL кладёт в один узел `Relation Name` — настоящее имя таблицы, `Schema` — схему, `Alias` — алиас отдельно. Из трёх популярных баз (MySQL, MariaDB, PostgreSQL) такой план строит только PostgreSQL: MySQL и MariaDB для целого класса обычных запросов плана не строят вовсе либо не называют в нём таблицу (однотабличная запись, чтение по ключу с известным значением), поэтому их `EXPLAIN` не может служить источником «какие таблицы трогает запрос». Версия движка и настройка формата плана этого не меняют. Поэтому движок ровно один — PostgreSQL.

Движок, отличный от PostgreSQL, отвергается **до** открытия соединения — по схеме DSN. Порядок
существен: с чужим DSN соединение не открывается вовсе, поэтому «не тот движок» не может
обернуться «база недоступна» — а это разные починки (там чинят адрес, здесь сам движок).

### Проверено на живых серверах

- PostgreSQL 14.5 и 18.4 — план отдаёт `Relation Name` (настоящее имя) и `Alias`; при `VERBOSE` ещё и `Schema`.
  Проверены CTE, производные таблицы, представления, `EXISTS`, `UNION`, самосоединение.

## Режим разработки

`DEV` в `app/config.php` (`true` или `false`) включает и выключает режим разработки, при включённом
режиме ошибки выводятся на экран.

## Проверка стиля кода

`php maws.php style` прогоняет PHP-CS-Fixer по правилам из `.php-cs-fixer.php`. Команда **правит файлы**;
чтобы только проверить, запускайте фиксер напрямую с `--dry-run`.

PHP-CS-Fixer не входит в зависимости Composer: это отдельный phar в каталоге `.tools/`, который не
хранится в репозитории. Перед первым запуском положите его туда:

```
mkdir .tools
curl -L https://github.com/PHP-CS-Fixer/PHP-CS-Fixer/releases/download/v3.95.27/php-cs-fixer.phar -o .tools/php-cs-fixer.phar
```

Версия 3.95.27 — та, под которую проверен стиль проекта. Последняя доступна по адресу
https://cs.symfony.com/download/php-cs-fixer-v3.phar. Пока файла нет, команда печатает эти же
инструкции и ничего не делает.

## Проверка контрактов

`php maws.php test` прогоняет контракты всего `core/**`: каждый файл с объявлением `#[Subject]`
получает свой тест и свой процесс, в конце — сводка «контрактов 50, прошло 50, провалено 0».

Тесты руками не пишутся. Тест — вывод контракта: команда читает атрибуты над классом и методами,
генерирует по ним обычный PHP-файл и запускает его. Файл перезаписывается при каждом прогоне, поэтому
правки в нём теряются — править надо контракт в исходнике. Генерированные тесты ядра лежат в
`app/Tests/Core/` зеркально `core/`. Устройство — в [HOWITTEST.md](HOWITTEST.md).

Прогону нужны зависимости из шага 1 и живая база из шага 2: без неё каждый контракт останавливается
строкой «Нет живой базы». Четыре контракта — `Man`, `Head`, `Legs`, `PlacePass` — работают на собранном
каркасе, поэтому до `make build` они падают, а после него проходят все 50.

## Проверка окружения

`php maws.php doctor` отвечает на вопрос «почему не работает» на новой машине: версия PHP (порог
берётся из `composer.json`), расширения, константы конфига, права на `logs/`, `db/migrations` и
временный каталог, доступность базы, версия фреймворка.

Каждая проверка — одна строка: `[ok]` в порядке, `[!!]` провал, `[??]` предупреждение (не работает
часть хелперов, сайт жив), `[--]` не проверялось — и тут же сказано почему. Код возврата 1 при любом
провале, поэтому команду можно ставить в деплой.

## Как начать работу

Первая рабочая страница — каркас, который собирает `make build`: направление `Public`, места `Home`
и `SecondPlace`, инструменты `ExampleTool` и `ExampleTool_1` у `Home` и `ExampleTool` у `SecondPlace`,
раздел «Главная страница», ведущий в `Home`, и нужда `Home` в инструменте соседнего места. Пока
каркаса нет, корень сайта отвечает ошибкой: главной страницы в базе ещё не существует.

1. Поставить зависимости:

   ```
   composer install
   ```

2. Указать реквизиты базы в `app/config.php` — константы `DBASE_DSN`, `DBASE_USER`, `DBASE_PASSWORD`.
   DSN начинается с `pgsql:`. Сама база должна существовать заранее: таблицы создаст миграция, а
   пустую базу она не заводит.

3. Создать структуру таблиц:

   ```
   php maws.php make migrate
   ```

4. Собрать каркас — направление, два места, главную страницу и три инструмента:

   ```
   php maws.php make build
   ```

   Миграции команда применяет сама, поэтому третий шаг можно и пропустить: он отдельный, чтобы
   видеть, что именно меняет базу.

5. Открыть корень сайта в браузере. Точка входа — `public/index.php`, поэтому корнем сайта настраивают
   каталог `public/`, а не корень проекта.

Страница покажет список из трёх строк: это `test_table`, которую наполняет миграция, а выводит
инструмент `ExampleTool`. `startWork()` места `Home` отдаёт то, что вернул `$tools->ExampleTool->serve()`.
В самом инструменте видно, из чего складывается ответ: `getTestData()` читает записи через
`Repository`, `showHTML()` отдаёт их шаблону, а `serve()` сводит одно с другим. Разметка при этом —
не обязанность инструмента, а один из выходов: `getTestData()` о шаблоне ничего не знает.
